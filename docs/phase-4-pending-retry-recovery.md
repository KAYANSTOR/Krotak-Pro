# Post-V1 Phase 4 — Pending / Retry / Recovery Hardening

**التاريخ:** 2026-09-13  
**الحالة:** منفذة في الكود والمستودع؛ الاعتماد النهائي مشروط بنجاح بوابة CI والاختبار الفعلي.

## النطاق

- الرسائل received وparsed وfailed تدخل مسار الاستعادة الموحد.
- الفشل التقني المؤقت يصبح failed مع سبب واضح؛ النتائج التجارية النهائية تبقى rejected أو parsed.
- إعادة المحاولة تعتمد على Audit Log الحالي، دون دفتر مالي أو طابور مالي ثانٍ.
- Backoff تصاعدي محدود: 30s، 60s، 120s ... حتى 30 دقيقة، وبحد أقصى 5 محاولات تلقائية.
- إعادة المحاولة اليدوية تتجاوز التأخير، ويمكنها فتح محاولة جديدة بعد الاستنفاد.
- النجاح يسجل message_retry_cleared وتبقى آثار المحاولات قابلة للتدقيق.
- recovery دوري كل دقيقة مع single-flight guard لمنع التنفيذ المتوازي.
- إشعارات المحافظ لا تُؤكّد على مستوى النقل عند فشل الحفظ المحلي قبل إنشاء IncomingMessage.

## عدم التكرار

تستمر المعالجة التجارية عبر UnifiedPaymentEventEngine ثم LocalTransferProcessor. لا يوجد ledger بديل لإعادة المحاولة، ومعرف العملية/مرجع السجل الحالي يحمي من إنشاء الحركة المالية نفسها مرتين.

## بوابة الاعتماد

لا تُعلن Production Ready قبل نجاح dart analyze وflutter analyze وflutter test وflutter build apk --debug، ثم اختبار Android فعلي للتوقف والاستئناف وفشل الإرسال وإعادة المحاولة والاستعادة.
