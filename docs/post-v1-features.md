# NET — ميزات ما بعد الخطة الأولى

## 1. الغرض من الوثيقة

تسجل هذه الوثيقة الميزات الجديدة المطلوبة بعد اكتمال الخطة الأولى لتطبيق NET. لا تُضاف هذه الميزات إلى نطاق MVP الأول إلا إذا تم اعتمادها صراحة. يجب تنفيذها فوق Domain وقاعدة البيانات ومحرك الأعمال المستقرين، وليس على شكل حالات واجهة محلية أو بيانات تجريبية.

المرجع الوظيفي لهذه الوثيقة هو قائمة ميزات إصدار Z Net 1.0.8 المرفقة من صاحب المشروع. مستودع Kotlin يبقى مرجعًا للتصميم فقط، ولا يُعامل كدليل على وجود تنفيذ فعلي لهذه الميزات.

## 3. الميزة الأولى: خدمة سلفني

### الهدف

تمكين المشترك المؤهل، الذي نفد رصيده، من استلام كرت طوارئ من أدنى فئة كروت نشطة، مع تسجيل مديونية تُسدّد تلقائيًا عند أول شحن أو تحويل لاحق.

### التدفق المطلوب

```text
SMS أو مصدر دفع وارد
  -> التعرف على طلب سلفني
  -> التأكد من تسجيل المشترك
  -> التأكد من أن الرصيد صفر تمامًا
  -> التأكد من عدم وجود مديونية سابقة
  -> اختيار أدنى فئة كروت نشطة
  -> حجز الكرت ذريًا
  -> تسجيل مديونية السلفة
  -> إرسال الكرت
  -> تسجيل التدقيق والنتيجة
  -> اقتطاع السلفة عند أول شحن أو تحويل مؤهل
```

### قواعد القبول

- يقبل النظام كلمات `سلفني` أو `س` أو `s` أو `salafni` بعد تعريف التطبيع اللغوي النهائي.
- يجب أن يكون المشترك موجودًا في دفتر الحسابات.
- يجب أن يكون الرصيد صفرًا تمامًا.
- يجب ألا توجد مديونية سابقة غير مسددة.
- اختيار الفئة يكون من أدنى فئة نشطة، مع عدم اختراع ترتيب بديل قبل اعتماد السياسة.
- الحجز والإدانة والإرسال والتدقيق يجب أن تملك استراتيجية تعويض عند فشل أي خطوة.
- إعادة إرسال نفس الطلب لا تنشئ سلفة ثانية.

### التغييرات المطلوبة

- كيان `Advance` مع الحالة، المبلغ، العميل، الكرت، المرجع، وتاريخ الإنشاء والسداد.
- `AdvanceRepository`.
- `AdvanceService`.
- قاعدة تمنع أكثر من سلفة مفتوحة حسب السياسة المعتمدة.
- ربط أول إيداع أو تحويل بعملية تسديد تلقائي.
- قوالب رسائل للقبول والرفض والتسديد.
- اختبارات للرصيد صفر، المديونية السابقة، عدم توفر المخزون، التكرار، وفشل الإرسال.

## 4. الميزة الثانية: قراءة إشعارات المحافظ

### الهدف

استقبال إشعارات المحافظ الإلكترونية كبديل أو مصدر مستقل عن SMS، مع اختيار مصدر الدفع لكل محفظة.

### المصادر المحتملة في المواصفة

تشمل الأمثلة جيب، الكريمي، ون كاش، وجوالي. لا يجوز افتراض شكل الإشعار أو اسم الحزمة أو صيغة البيانات قبل جمع عينات حقيقية واختبارها على أجهزة فعلية.

### التدفق المطلوب

```text
Notification Listener
  -> حفظ الإشعار الخام
  -> تحديد مصدر المحفظة
  -> تحليل القالب
  -> إنشاء بصمة رقمية
  -> منع التكرار
  -> تحويل الإشعار إلى ParsedTransfer
  -> تمرير المعالجة إلى TransferProcessor
```

### التغييرات المطلوبة

- كيان `PaymentSource` يحدد المحفظة ومصدرها: SMS أو notification.
- كيان `IncomingNotification` أو توحيد الرسائل الواردة ضمن `PaymentMessage` بمصدر واضح.
- Android Native Notification Listener Service.
- طبقة Bridge بين Kotlin وDart.
- `NotificationParser` مستقل عن `MessageParser` مع مخرج موحد.
- بصمة عملية تشمل المصدر والمرجع والمبلغ والوقت والجهة بعد اعتماد سياسة البصمة.
- إعدادات تفعيل أو تعطيل المصدر لكل محفظة.
- اختبارات parser بعينات منزوعة البيانات الحساسة.

### مخاطر وقرارات

- صلاحية Notification Listener حساسة ويجب شرحها للمستخدم.
- بعض المحافظ قد تغير صيغة الإشعار دون ضمان ثباتها.
- يجب تحديد هل تتم معالجة الإشعار عند ظهوره فقط أم توجد آلية استعادة.
- يجب تحديد سياسة التخزين الآمن للنص الخام.

## 5. الميزة الثالثة: التسوية التلقائية لنقاط البيع

### الهدف

عند وصول حوالة مخصصة لنقطة بيع، يتعرف النظام على نقطة البيع، ويسجل تسوية تقلل المديونية، ويرسل إشعارًا بالمبلغ والرصيد المتبقي.

### التدفق المطلوب

```text
Payment Message
  -> التعرف على نقطة البيع
  -> التحقق من أن التسوية التلقائية مفعلة
  -> تسجيل حركة تسوية ذرية
  -> تخفيض المديونية
  -> إنشاء Audit Log
  -> إرسال SMS تأكيدي
```

### التغييرات المطلوبة

- ربط `PointOfSale` بمعرفات دفع متعددة.
- كيان أو سجل `Settlement` كامل.
- رصيد مديونية واضح وقابل للتدقيق.
- `PointOfSaleService` و`SettlementService`.
- إعداد `autoPosSettlementEnabled`.
- قوالب نجاح وفشل وتأكيد.
- منع التسوية المكررة بنفس المرجع أو البصمة.
- اختبار التسوية الجزئية والكاملة، الرصيد السالب، نقطة بيع غير معروفة، وفشل SMS.

## 6. الميزة الرابعة: بث SMS للعملاء

### الهدف

تمكين صاحب الشبكة من إرسال رسالة إدارية جماعية للعملاء المسجلين، مع استبعاد الأرقام المحظورة أو التالفة وإظهار تقدم الإرسال.

### التدفق المطلوب

```text
اختيار البث
  -> حساب المستلمين المؤهلين
  -> استبعاد المحظور والتالف
  -> عرض ملخص وعدد المستلمين
  -> تأكيد صريح
  -> إنشاء Broadcast Job
  -> إرسال على دفعات
  -> تسجيل نجاح وفشل كل رقم
  -> عرض التقدم والنتيجة النهائية
```

### التغييرات المطلوبة

- كيان `BroadcastJob`.
- كيان `BroadcastRecipient`.
- حالات المهمة: draft، confirmed، running، paused، completed، partiallyFailed، failed، cancelled.
- طابور إرسال محدود ومراقب، وليس حلقة واجهة.
- سجل نتائج لكل مستلم.
- حماية من الإرسال المكرر.
- تأكيد قبل الإرسال مع نص الرسالة وعدد المستلمين.
- إعدادات معدل الإرسال وإعادة المحاولة.
- فصل رسائل البث الإداري عن رصيد ترخيص الكروت حسب القرار التجاري النهائي.

### مخاطر

- صلاحيات SMS وسياسات Google Play.
- التكلفة ومعدل الإرسال.
- الإرسال العرضي واسع النطاق؛ يجب اعتباره عملية حساسة قابلة للتأثير المالي والتشغيلي.
- ضرورة وجود إلغاء أو إيقاف للمهمة إن كان Android يسمح بذلك أثناء التنفيذ.

## 7. الميزة الخامسة: تحسين التعرف وربط الحسابات المتعددة

### الهدف

رفع دقة التعرف على العميل عند تعدد أرقامه ومعرفاته، ومنع الازدواجية، وضمان بقاء الحركات مرتبطة بالعميل الصحيح بعد الدمج.

### التغييرات المطلوبة

- فهرس فريد للمعرفات النشطة بعد اعتماد قواعد التطبيع.
- تطبيع أرقام الهاتف حسب الدولة والصيغة المعتمدة.
- سجل Alias أو CustomerIdentifier تاريخي.
- خدمة `CustomerIdentityResolver`.
- سجل دمج `CustomerMerge` يحفظ المصدر والوجهة والسبب والمنفذ والوقت.
- سياسة واضحة للمراجع والحركات بعد الدمج.
- منع ربط معرف واحد بعميلين نشطين.
- شاشة مراجعة عند وجود تطابقات متعارضة بدل الاختيار الصامت.

### اختبارات القبول

- رقم أساسي ورقم بديل لنفس العميل.
- اختلاف صيغ الرقم.
- مرجع تحويل يستخدم معرفًا بديلًا.
- عميلان لهما معرف متشابه.
- دمج عميلين مع حفظ جميع الحركات.
- محاولة إعادة استخدام معرف مرتبط بعميل نشط.

## 8. تحسينات UI/UX والأداء

### التعديل بالضغط المطول

إضافة Long Press على بطاقة المحفظة أو نقطة البيع لفتح التعديل. يجب توفير بديل وصول واضح للذين لا يستخدمون الضغط المطول، مثل قائمة إجراءات أو زر تحرير.

### التباين والوضعان الليلي والنهاري

يجب مراجعة Design Tokens الحالية، وقياس التباين، وحالات الحقول والأزرار والرسائل والتنبيهات في الوضعين. لا يكفي تعديل اللون بصريًا دون اختبار نصوص RTL والأيقونات وحالات disabled.

### Pending Confirmations وإعادة الإرسال

يجب تحويل العملية قيد التأكيد إلى Job قابلة للاستعادة، مع معرف idempotency وحالة واضحة ومحاولات محدودة وسجل آخر خطأ. لا يجوز أن تعتمد إعادة الإرسال على حالة Widget.

### استيراد دفعات الكروت

يجب تصميم استيراد streaming أو batch، والتحقق من الملف قبل الإدخال، وتحديد أخطاء كل صف، واستخدام معاملات على دفعات، وعرض تقدم حقيقي. يجب منع تكرار serial number أو secret code قبل اعتماد السجلات.

## 11. تغييرات قاعدة البيانات والمigrations

يجب أن تأتي هذه الميزات عبر migrations منفصلة بعد Schema v1، وليس بتعديل صامت للجداول الحالية. كل migration يجب أن يتضمن:

- رقم إصدار واضح.
- ترحيلًا قابلًا للاختبار.
- اختبار قاعدة فارغة.
- اختبار ترقية قاعدة بيانات قديمة.
- اختبار الحفاظ على السجل المالي.
- خطة rollback أو آلية استعادة قبل الترقية.

## 12. معايير الإصدار اللاحق

لا تعتبر ميزات ما بعد الخطة الأولى مكتملة إلا عند تحقق الشروط التالية:

1. كل عملية مالية لها idempotency وAudit Log.
2. كل مصدر دفع يحفظ الرسالة أو الإشعار الخام قبل التحليل.
3. لا توجد عملية تعتمد على استمرار Flutter UI في الذاكرة.
4. يوجد اختبار انقطاع وإعادة تشغيل لكل Job خلفية.
5. توجد اختبارات parser على عينات حقيقية منزوعة البيانات الحساسة.
6. توجد مراجعة لصلاحيات SMS وNotification Listener وسياسة النشر.
7. يوجد تأكيد قبل البث الجماعي وسجل تفصيلي لنتيجة كل مستلم.
8. يمكن استعادة قاعدة البيانات بعد migration دون فقدان الحركات.
9. لا توجد بيانات Mock داخل Release build.

## 13. قرارات مطلوبة قبل بدء هذه المرحلة

- هل السلفة الواحدة مسموحة لكل عميل أم توجد فترة انتظار؟
- ما تعريف الرصيد صفر عند وجود كسور أو حركات pending؟
- ما أقل فئة عند وجود عدة عملات أو أسعار؟
- ما المحافظ المدعومة فعليًا في الإصدار الأول؟
- ما شكل عينات SMS والإشعارات لكل محفظة؟
- كيف يتم التعرف على نقطة البيع؟
- هل يسمح بالبث لكل العملاء أم لفئات أو حالات محددة؟
- ما معدل الإرسال المسموح وما سياسة التكلفة؟
- هل رسائل البث تستهلك رصيدًا مستقلًا أو لا تستهلك ترخيص الكروت؟
- ما قواعد دمج العملاء النهائية؟
- ما الأجهزة وإصدارات Android المستهدفة لمعالجة SMS والإشعارات؟

## 14. تعريف الانتهاء

تنقل هذه الوثيقة إلى حالة التنفيذ فقط بعد اعتماد قرارات القسم السابق. بعدها تنفذ الميزات بالترتيب P0 ثم P1 ثم P2، وكل ميزة تمر بدورة Domain، Database، Repository، Service، Native Bridge عند الحاجة، UI، Tests، ثم Release Notes.
