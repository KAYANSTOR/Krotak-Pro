# GitHub Foundation Audit — NET Flutter

**التاريخ:** 2026-09-17  
**المستودع:** `KAYANSTOR/net-flutter`  
**الفرع المرجعي:** `main`  
**الغرض:** تثبيت خط أساس قابل للمراجعة قبل بدء المرحلة الأولى. هذا التقرير لا يغيّر منطق التطبيق.

## 1. نطاق التدقيق

تمت مراجعة شجرة ملفات المستودع من GitHub، بما يشمل كود Flutter، طبقات Domain وData، شاشات UI، ملفات Android، الاختبارات، الوثائق، وملفات GitHub Actions. كما تمت مراجعة بنية CI الحالية وآخر تشغيلات workflow.

## 2. البنية الحالية

المشروع تطبيق Android مبني بـ Flutter وDart ويستخدم Drift/SQLite للتخزين المحلي. المعمارية المعلنة هي:

```text
UI → AppContainer → Domain services/use cases → Repositories → Drift SQLite
                                                    ↓
                                      Android SmsReceiver + Channels
```

توجد طبقات فعلية للرسائل، العملاء، الكروت، المخزون، البيع، التحويلات، التسوية، سلفني، العروض، التقارير، النسخ الاحتياطي، التفعيل، الإعدادات، والاسترداد. توجد كذلك مجموعة واسعة من اختبارات Domain وDatabase وServices وWidgets.

## 3. دورة العمل الحرجة

الدورة التي يجب تثبيتها قبل إضافة ميزات جديدة هي:

```text
استقبال SMS
→ حفظ الرسالة الخام
→ بصمة ومنع التكرار
→ تحليل القالب والحقول
→ التحقق من العميل والحظر والمخزون وPOS
→ حجز الكرت ذريًا
→ تسجيل البيع والقيد والدين/الرصيد
→ إنشاء مهمة الإرسال
→ الإرسال عبر SIM
→ تسجيل النتيجة
→ إغلاق أو إعادة محاولة أو استرداد
```

يجب ألا تعتمد هذه الدورة على Widget أو ذاكرة مؤقتة. يجب أن تكون قابلة للاستئناف بعد إغلاق التطبيق أو إعادة تشغيل الجهاز.

## 4. نقاط القوة الحالية

- وجود Domain entities وخدمات محلية حقيقية بدل واجهات فقط.
- وجود Drift/SQLite ومستودعات محلية.
- وجود `SmsReceiver` وطبقة Bridge بين Android وFlutter.
- وجود خدمات لتحليل الرسائل، الاسترداد، إعادة المحاولة، البيع، التسوية، سلفني، العروض، والنسخ الاحتياطي.
- وجود شاشات تشغيلية للرسائل والعملاء والمخزون والتقارير والإعدادات.
- وجود اختبارات متعددة تغطي أجزاء من المجال والخدمات.
- وجود GitHub Actions يفحص التحليل والاختبارات ويبني APK.

## 5. مخاطر التثبيت قبل المرحلة الأولى

### 5.1 العقود

يجب توحيد عقود repositories وservices و`Result<T>` بين الإنتاج والاختبارات. أي اختلاف بين Fake وimplementation سيمنع اعتبار الاختبار دليلًا موثوقًا.

### 5.2 الذرية

الحجز والبيع والقيد وتحديث الدين وإنشاء مهمة الإرسال تحتاج حدودًا ذرية أو Workflow تعويضيًا واضحًا. فشل الإرسال لا يجوز أن يؤدي إلى صرف كرت ثانٍ قبل التحقق من نتيجة المحاولة السابقة.

### 5.3 idempotency

يجب فرض uniqueness على مستوى قاعدة البيانات لمراجع الرسائل والعمليات والتسويات والحجوزات وتسليم الكود. الفحص السابق للإدخال وحده لا يكفي عند التشغيل المتوازي.

### 5.4 الاسترداد

كل مهمة معلقة تحتاج حالة، وعدد محاولات، ووقت المحاولة التالية، وسبب الفشل، وقفلًا قابلًا للاسترداد. إعادة المحاولة لا يجب أن تعتمد على دورة حياة الشاشة.

### 5.5 Android

وجود Bridge لا يثبت التشغيل على جهاز فعلي. يلزم اختبار SMS عند إغلاق التطبيق، Boot، تحسين البطارية، SIM واحدة ومزدوجة، وفشل الشريحة والتحويل التلقائي.

### 5.6 النسخ الاحتياطي

تصدير JSON وحده لا يساوي نسخة إنتاجية. المطلوب تشفير، سلامة ملف، إصدار مخطط، استعادة إلى قاعدة مؤقتة، تحقق، ثم اعتماد ذري.

## 6. GitHub Actions الحالية

الـ workflow الحالي ينفذ:

```text
flutter pub get
flutter analyze --no-fatal-infos
flutter test
flutter build apk --release
```

ويقوم برفع APK كـ artifact، كما ينشئ GitHub Release عند الدفع إلى `main`. لذلك ستكون نتائج هذا الفرع هي خط الأساس الرسمي قبل المرحلة الأولى.

## 7. خطة المرحلة الأولى بعد اعتماد التدقيق

1. تشغيل CI جديد على فرع العمل وعدم تفسير نجاح سابق على أنه ضمان حالي.
2. جمع أخطاء `analyze` و`test` و`build` من GitHub Actions.
3. توثيق العقود الحالية والمتعارضة في ملف واحد.
4. تثبيت العقد النهائي للمستودعات والخدمات وأنواع النتائج.
5. تحديث الاختبارات وFakes لتتبع العقد نفسه.
6. تشغيل CI مرة أخرى حتى تصبح النتائج قابلة للتكرار.
7. عدم إضافة ميزات جديدة قبل اجتياز هذه البوابة.
