# NET Flutter — خطة التنفيذ الأولية

## الحالة الحالية

اكتملت البنود 1–3 والجزء الأول من البند 4: النطاق، الكيانات، قاعدة البيانات، العملاء والمحافظ والفئات والمخزون، ثم البيع من الرصيد وعكسه. التفاصيل في [progress.md](progress.md).

البند التالي: تنفيذ `MessageParser` و`TransferProcessor`.

## مصدر الحقيقة

مواصفات NET الوظيفية هي مصدر الحقيقة للمنطق التجاري. مستودع Kotlin هو مرجع بصري للواجهات والتنقل والمكونات فقط. القيم الافتراضية الموجودة في Prototype لا تُنقل كبيانات إنتاجية.

## المعمارية

```text
Flutter UI
  -> State Management
  -> Domain Use Cases
  -> Repositories
  -> Local Database
  -> Android Native Bridge for SMS
  -> License/Sync/Backup API when required
```

## ترتيب التنفيذ

1. تثبيت نطاق المنتج وقواعد البيع والترخيص.
2. تصميم الكيانات والعلاقات وقاعدة البيانات المحلية.
3. تنفيذ العملاء والمحافظ وفئات الكروت والمخزون.
4. تنفيذ البيع والحجز والتسويات والعكس.
5. تنفيذ MessageParser وTransferProcessor.
6. تنفيذ Android SMS Receiver والخدمة الخلفية والجسر مع Flutter.
7. تنفيذ التفعيل والترخيص والنسخ الاحتياطي والاستعادة.
8. نقل واجهات Kotlin إلى Flutter وربطها بالـUse Cases.
9. إضافة الاختبارات الوظيفية والتكاملية واختبارات Android Native.
10. تجهيز CI والإصدار التجريبي ثم الإنتاج.

## قواعد غير قابلة للتفاوض

- لا عملية مالية داخل Widget.
- لا اعتماد على Backend لكل عملية يومية.
- لا بيع أو حجز دون Transaction ذرية وAudit Log.
- لا معالجة SMS دون منع التكرار وإمكانية الاستعادة.
- لا أسرار أو بيانات عملاء في Git أو logs الإنتاج.
- لا اعتماد على بيانات Mock خارج الاختبارات.
