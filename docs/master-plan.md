# خطة إعادة بناء NET من الصفر إلى الإنتاج

## 1. الهدف والنطاق

إعادة بناء تطبيق **NET** بالكامل باستخدام Flutter وDart، مع الحفاظ على تصميم وتجربة وتدفقات واجهات مستودع Kotlin الحالي كمرجع بصري ووظيفي، دون تحويل Kotlin سطرًا بسطر.

مصادر الحقيقة مرتبة كما يلي:

1. مواصفات NET الوظيفية المرفقة.
2. أي سلوك مثبت فعليًا في مستودع Kotlin الحالي.
3. القرارات المعمارية المعتمدة في هذه الخطة.
4. لا تُعتبر قيم `remember { mutableStateOf(...) }` أو البيانات الافتراضية في الواجهة Business Logic حقيقية.
5. لا يُفترض وجود Backend أو API أو قاعدة بيانات إلا بعد تصميمها وتنفيذها والتحقق منها.

النتيجة المستهدفة هي تطبيق Android أولًا، يعمل **Local-first**، ويستطيع تنفيذ العمليات اليومية ومعالجة SMS دون إنترنت، مع استخدام الإنترنت للتفعيل والتحقق من الترخيص والمزامنة والنسخ الاحتياطي عند الحاجة.

## 2. الوضع الحالي الذي ستبدأ منه الخطة

المستودع الحالي هو Prototype لواجهة Android مبني بـ Kotlin وJetpack Compose. يحتوي على شاشات ومسارات تنقل ومكونات تصميم جيدة، لكنه لا يحتوي على طبقة تشغيل تجارية مكتملة. الحالات تُنشأ داخل `MainActivity`، والبيانات التجارية ثابتة أو محلية، ولا توجد طبقة مستخدمة فعليًا لـ Room أو Retrofit أو Repository أو Backend أو Authentication.

سيُستخدم المستودع الحالي في البداية لاستخراج:

- أسماء الشاشات وترتيبها.
- تدفقات التنقل.
- حالات الواجهة الموجودة.
- المكونات المرئية القابلة لإعادة الاستخدام.
- الألوان والخطوط والأيقونات والأصول.
- النصوص العربية والـRTL.

لن يُستخدم لتقرير منطق العمليات المالية أو قواعد بيع الكروت أو معالجة SMS؛ هذه الوظائف ستُبنى من مواصفات NET وتُثبت باختبارات.

## 3. القرار المعماري المقترح

### 3.1 البنية العامة

```text
Flutter UI
    |
Application / State Management
    |
Domain Use Cases and Business Rules
    |
Repositories
    |-------------------------|
Local Database             Remote License/Sync API
    |
Android Native Bridge
    |
SMS Receiver / Processor / Sender / Background Execution
```

### 3.2 المبادئ الإلزامية

- **Local-first:** القراءة والكتابة اليومية من قاعدة البيانات المحلية.
- **Offline-capable:** البيع، المخزون، أرصدة العملاء، القوالب، والتقارير الأساسية لا تعتمد على الإنترنت.
- **Transactional:** كل عملية مالية أو حجز كرت يجب أن تكون ذرية وقابلة للتدقيق.
- **Idempotent:** وصول SMS أو إعادة تنفيذ مهمة لا يكرر الإيداع أو البيع.
- **Auditable:** كل تغيير مالي أو مخزني يسجل في سجل حركات غير قابل للالتباس.
- **Secure by default:** لا أسرار داخل التطبيق أو Git، ولا تسجيل لمفاتيح التفعيل أو بيانات العملاء.
- **Feature-by-feature:** لا يتم بناء جميع الشاشات شكليًا ثم تأجيل المنطق؛ كل ميزة تُبنى من Domain إلى Database إلى Service إلى UI إلى Tests.
- **Native where necessary:** معالجة SMS وخدمات Android الخلفية تكون عبر طبقة Native/Platform Channel عند الحاجة، وليست مسؤولية Flutter UI وحدها.

### 3.3 خيارا التنفيذ المعماري

| الخيار | المزايا | التنازلات | القرار |
|---|---|---|---|
| Flutter كامل مع إضافات جاهزة لـSMS والخلفية | سرعة أولية أعلى وعدد ملفات Native أقل | قيود Android، صعوبة الضمان في الخلفية، واحتمال عدم كفاية الإضافات لمعالجة SMS الحساسة | مناسب للنموذج الأولي فقط |
| Flutter للواجهة والمنطق المشترك مع Android Native Bridge لـSMS | تحكم أفضل في BroadcastReceiver والخدمة الخلفية والصلاحيات والبطارية | يحتاج Kotlin Native محدودًا واختبارات Android إضافية | **الخيار الموصى به** |

لن يتم اختيار Backend مركزي لكل عملية يومية؛ هذا يخالف شرط التشغيل دون إنترنت. Backend مطلوب فقط للتفعيل والتحقق من الترخيص والمزامنة والنسخ الاحتياطي أو وظائف يثبت احتياجها لاحقًا.

## 4. مراحل التنفيذ من البداية إلى النهاية

### المرحلة 0: تثبيت القرارات ونطاق المنتج

**الهدف:** منع بدء التطوير قبل إغلاق القرارات التي تغير بنية النظام.

**المخرجات:**

- وثيقة Product Scope.
- تعريف المستخدم الأساسي: صاحب أو مزود شبكة الإنترنت.
- قائمة الوظائف الأساسية والوظائف المؤجلة.
- تعريف ما يعمل دون إنترنت وما يتطلب إنترنت.
- قرار سياسة الترخيص والتفعيل.
- قرار سياسة النسخ الاحتياطي والاستعادة.
- قرار سياسة SMS والرقم المستخدم للإرسال.
- قاموس المصطلحات العربية والإنجليزية.

**معيار القبول:** لا توجد ميزة في قائمة التنفيذ بلا تعريف لمدخلاتها ومخرجاتها وقواعد فشلها ومصدر بياناتها.

### المرحلة 1: توثيق مرجع Kotlin وUX

**الهدف:** تحويل Prototype الحالي إلى مرجع قابل للتنفيذ، لا إلى كود يُنسخ.

**الأعمال:**

- تثبيت قائمة الشاشات الـ25 الموجودة.
- توثيق مسارات التنقل، التبويبات، Dialogs، Bottom Sheets، وحالات الرجوع.
- تسجيل لقطات مرجعية لكل شاشة وحجم شاشة.
- استخراج Design Tokens: الألوان، المسافات، الزوايا، الظلال، أحجام النص، الخطوط، RTL.
- تصنيف كل شاشة إلى: إنتاجية أساسية، إدارة، تقارير، إعدادات، مساعدة، أو مؤجلة.
- توثيق الفرق بين UI موجود فعليًا وميزة مذكورة في المواصفات لكنها غير ممثلة في Kotlin.

**معيار القبول:** يمكن لمصمم أو مطور Flutter تنفيذ الشاشة من وثيقة UX دون الرجوع إلى Kotlin إلا للتحقق البصري.

### المرحلة 1A: متطلبات الشاشات والوظائف المؤكدة من مرجع Kotlin

أثبتت مراجعة شاشات Kotlin وجود واجهات ومكونات لهذه المجالات: Dashboard، الحسابات والعملاء، الكروت والفئات، المحافظ ونقاط البيع، القوالب، التقارير والسجلات، الإعدادات، البطارية وشرائح الاتصال، مركز المساعدة، التفعيل، والتنقل السفلي. ما يلي هو مواصفة NET المعتمدة لهذه المجالات، مع اعتبار أن وجود واجهة Kotlin لا يعني اكتمال منطقها التجاري.

#### Dashboard والتنقلات

- أيقونة المساعدة في الشاشة الرئيسية تكون فعالة وتفتح مركز مساعدة يحتوي على مقالات وإرشادات قابلة للفتح والإغلاق، وليس شاشة شكلية.
- زر `+` في الشاشة الرئيسية يفتح Bottom Sheet للإجراءات السريعة، ويتيح على الأقل: البيع المباشر، حسابات/ملخصات نقاط البيع، وإضافة عميل.
- الضغط على عدد الكروت يفتح Bottom Sheet يعرض إجمالي المخزون وتوزيعه حسب الفئات والحالات.
- الضغط على مبيعات اليوم ينقل إلى تقرير مبيعات اليوم، والضغط على مبيعات الشهر ينقل إلى تقرير مبيعات الشهر.
- تقارير المبيعات تعرض مصدر العملية أو المحفظة، مثل: جيب، جوالي، ون كاش، وغيرها، وعدد الكروت المباعة وقيمة المبيعات.
- قسم آخر العمليات يظهر أسفل Dashboard ويعرض العمليات الحديثة الفعلية مع إمكانية فتح سجل العمليات الكامل.
- كل بطاقة أو إجراء يجب أن يملك Route أو Callback حقيقيًا؛ لا يُستخدم SnackBar كبديل للتنقل.

#### البيع المباشر

مسار البيع المباشر يبدأ بتحديد العميل، ثم فئة الكرت، ثم تأكيد الإرسال والتسجيل. يجب أن يدعم نوع العملية المحدد في مواصفات المنتج: نقد، آجل، أو تحويل من محفظة أخرى. لا يُفترض أن الاتصال الهاتفي قبل الإيداع عملية مالية تلقائية؛ يُسجل كحالة بيع يدوي أو طلب معلق فقط بعد تحديد قواعده واعتمادها.

البيع المباشر يستخدم فئات الكروت التي يضيفها المستخدم من شاشة الكروت، ولا ينشئ فئات أو أسعارًا ثابتة داخل الكود. يجب أن يمر عبر `CardInventoryService` و`SaleService` وLedger/Audit، مع منع صرف كرت غير متاح أو تكرار العملية.

#### إعدادات معالجة الرسائل

تُضاف إلى إعدادات التطبيق، وتُحفظ محليًا كإعدادات حقيقية، الخيارات التالية:

- **المعالجة التلقائية للرسائل:** عند إيقافها لا تُستقبل أو تُعالج التحويلات آليًا، وتبقى الرسائل محفوظة وفق سياسة الاستعادة.
- **معالجة مبالغ الفئات فقط:** عند تفعيلها لا تُعالج تلقائيًا إلا الرسائل التي يطابق مبلغها قيمة فئة موجودة في النظام.
- **معالجة الرسائل القديمة عند التوقف:** إعادة معالجة الرسائل التي وصلت أثناء إغلاق التطبيق أو توقفه عند عودته للعمل.
- **تفعيل/تعطيل الإرسال التلقائي:** إعداد مستقل لمسار إرسال الكرت بعد نجاح المعالجة والحجز.
- **إدارة فئات المبالغ:** فتح شاشة تعديل الفئات الموجودة، دون إنشاء فئة تلقائيًا من رسالة واردة.
- **إعدادات البطارية والتشغيل في الخلفية:** ربطها بإرشادات وصلاحيات Android الفعلية.
- **إعدادات SIM:** إدارة شريحة القراءة والإرسال وFailover وفق ما تسمح به المنصة.

#### المخزون والنفاد

- عند نفاد كروت فئة مطابقة، لا يُسجل البيع بنجاح ولا يُرسل كرت غير موجود.
- يمكن تفعيل إشعار نفاد لفئة محددة مع تحديد سقف التنبيه، مثل عدد أو نسبة متبقية.
- يمكن تعريف قالب رسالة نفاد خاص من إدارة قوالب الرسائل، ويُستخدم لإبلاغ العميل بأن الفئة غير متوفرة وطلب التواصل مع الإدارة، وفق إعداد الإرسال المعتمد.
- لا يُحرر الحجز تلقائيًا عند فشل الإرسال إذا كانت سياسة إعادة المحاولة تتطلب إبقاءه؛ تتم إعادة المحاولة وفق Delivery State ومدة الحجز المعتمدة، مع منع البيع المتزامن.

#### التحويلات غير المطابقة والمراجعة

إذا وصل مبلغ لا يطابق فئة موجودة، فلا يُنفذ بيع تلقائي. تُرسل إشعارات Android تفاعلية للمستخدم تتضمن التأكيد أو الرفض. عند التأكيد يُسجل المبلغ في حساب العميل وفق Workflow معتمد، وعند الرفض تُسجل النتيجة بسبب واضح. لا يجوز اختراع فئة أو اختيار كرت مختلف تلقائيًا.

إذا كان المعرّف غير محلول، يسمح النظام بإضافة Customer Identity Mapping ثم إعادة معالجة الرسالة نفسها بأمان، مع الحفاظ على idempotency وعدم إنشاء إيداع أو بيع مكرر.

#### القوالب وإدارة المحافظ

- تُضاف القوالب الافتراضية للمحافظ اليمنية المدعومة فعليًا في المنتج، ومنها جيب وجوالي وون كاش وفلوسك بعد التحقق من صيغ الرسائل الحقيقية.
- يمكن للمستخدم إضافة محافظ أو قوالب أخرى من داخل التطبيق.
- يدعم القالب حالات التحويل المشترك، والاسم المخفي، ورقم الحساب أو الرقم البديل، مع تصنيف المعرّف وعدم معاملته دائمًا كرقم هاتف.
- إنشاء القالب المخصص لا يتطلب كتابة Regex أو كود برمجي من المستخدم؛ يلصق المستخدم مثال الرسالة ويحدد من خلال واجهة مرئية موضع المبلغ والهاتف والحساب/الاسم والمرجع، ثم يحدد القالب الافتراضي والأولوية والتفعيل.
- يجب أن يمر القالب المخصص عبر نفس Template Engine للقوالب الافتراضية، مع شاشة محاكاة واختبار قبل التفعيل.
- تشمل إدارة القوالب قوالب رسائل العملاء، ورسالة نفاد الفئة، وقوالب نقاط البيع، مع تحديد القالب الافتراضي لكل نوع.

#### التقارير والسجلات

شاشة التقارير ليست ملخصًا فقط، بل مركز وصول إلى:

- سجل العمليات التفصيلي.
- تقارير المبيعات اليومية والشهرية مع المحفظة والفئة وعدد الكروت.
- حسابات أو ملخصات نقاط البيع ورسائل الملخص عند تفعيلها، دون إدخال نظام ديون أو إدارة موزعين.
- الرسائل المعلقة.
- الرسائل التي وصلت أثناء توقف الهاتف أو التطبيق.
- الرسائل المرفوضة والفاشلة وأسبابها.

كل تقرير يجب أن يعتمد على Repositories وبيانات حقيقية، ويعرض حالات Loading/Empty/Error، ولا يستخدم أرقامًا ثابتة.

#### النسخ الاحتياطي والاستعادة

يجب توفير إجراء واضح لنسخ بيانات التطبيق وإعداداته كاملة، وإجراء مستقل للاستعادة مع:

- التحقق من سلامة النسخة وتوافق إصدار المخطط.
- منع استبدال البيانات الحالية دون تأكيد واضح.
- تسجيل نتيجة النسخ والاستعادة في Audit أو سجل النظام.
- حماية النسخة من كشف بيانات العملاء والقوالب الحساسة.

#### استيراد الكروت والأصول البصرية

- شاشة الكروت توفر استيرادًا من CSV وExcel وPDF بعد تحديد قواعد استخراج الأعمدة والتحقق من التكرار والفئة.
- الاستيراد لا يعتمد مباشرة على اسم الملف؛ يجب عرض معاينة ونتيجة التحقق قبل الحفظ.
- كل كرت يرتبط بفئة يضيفها المستخدم، مع منع الكروت المكررة أو غير الصالحة.
- تُنقل أيقونات الفئات ومكونات الشاشات التي تفتقر إلى أيقونات تجميلية إلى Design System موحد في Flutter، دون نسخ ألوان ثابتة من Kotlin خارج Tokens المعتمدة.

#### الإشعارات والتسجيل التلقائي

- بعد نجاح إرسال الكرت، تُسجل العملية تلقائيًا كبيع ناجح وتُحدّث Sale وLedger/Transaction وAudit.
- يجب أن تكون نتيجة الإرسال قابلة للاسترداد وألا تؤدي إعادة المحاولة إلى إرسال أو تسجيل مكرر.
- الإشعارات التفاعلية لا تتخذ قرارًا ماليًا إلا بعد ضغط المستخدم على تأكيد أو رفض، وتُحفظ نتيجة القرار.

### المرحلة 3: تصميم قاعدة البيانات المحلية

**الهدف:** إنشاء مخزن موثوق للعمل دون إنترنت.

**الأعمال:**

- اختيار قاعدة محلية مناسبة لـFlutter، مثل SQLite عبر Drift أو بديل مكافئ يدعم migrations والمعاملات.
- تعريف الجداول والعلاقات والـindexes.
- تصميم migrations من الإصدار الأول.
- إضافة قيود uniqueness للعملاء والمعرفات والكروت والمراجع.
- تصميم سجل Audit منفصل.
- تصميم Transaction boundary لعمليات البيع والاستلام والحجز والعكس.
- تصميم سياسة حذف البيانات: soft delete للبيانات المالية، وحذف فعلي محدود للبيانات المؤقتة.
- تصميم تشفير قاعدة البيانات أو حماية الحقول الحساسة حسب مستوى المخاطر.

**الفهارس الأولية:** رقم العميل، معرفات العميل، رقم الكرت، حالة الكرت، فئة الكرت، تاريخ الحركة، نقطة البيع، مرجع SMS، وحالة الرسالة.

**معيار القبول:** اختبارات قاعدة البيانات تنجح على قاعدة فارغة، وبعد migration، وبعد rollback منطقي للعمليات المدعومة.

### المرحلة 4: طبقة التطبيق والحالة

### المرحلة 6A: ذكاء رسائل التحويل وحل هوية العميل

**الاسم المعتمد:** Payment Message Intelligence / Incoming Transfer Recognition.

هذه مرحلة امتداد للنظام الحالي وليست نظامًا موازيًا أو تحويلًا حرفيًا من `SmsParser.kt` إلى Dart. الهدف هو فصل مصدر المال عن هوية العميل وعن رقم تسليم الخدمة، مع إعادة استخدام `SMS Bridge` و`Incoming Message Handler` و`MessageParser` و`TransferProcessor` وRepositories الحالية بعد فحصها.

#### التدفق المعتمد

```text
SMS خام
  -> Template Matching
  -> Structured Parsed Transaction
  -> Identifier Resolution
  -> Customer Identity Mapping
  -> Existing Payment/Card Delivery Workflow
```

#### نموذج القالب

القالب يحدد مواقع البيانات داخل الرسالة باستخدام المتغيرات الأساسية:

- `%amount`: قيمة التحويل.
- `%phone`: رقم هاتف المرسل القابل للإرسال مباشرة.
- `%account`: رقم حساب أو اسم أو كود مرجعي أو معرف غير قابل للإرسال مباشرة.

يجب أن تكون القوالب الافتراضية والقوالب المخصصة امتدادًا لمحرك واحد. القالب المخصص لا ينشئ Parser ثانيًا، ويجب تخزينه بطريقة قابلة للتعديل والتفعيل والتعطيل والاختبار والتشخيص.

#### نتيجة التحليل

ينتج Parser رسالة منظمة فقط، ولا يتخذ قرارًا تجاريًا ولا يرسل كرتًا. يجب أن تتضمن النتيجة على الأقل:

- المبلغ والعملة.
- مصدر الرسالة أو تعريف القالب.
- المعرّف المستخرج.
- نوع المعرّف المصنف صراحةً: `phone` أو `account` أو `reference` أو `name` أو `unknown`.
- حالة التحليل وسبب الفشل عند عدم المطابقة.
- مرجع الرسالة أو التحويل لضمان idempotency.

#### حل هوية العميل

إذا كان المعرّف هاتفًا، يُستخدم وفق قواعد النظام الحالية بعد التحقق من صلاحيته. وإذا كان من نوع `account` أو `reference` أو `name`، فلا يجوز إرساله كرقم هاتف. يجب أن يمر عبر:

```text
Transfer Identifier -> Customer Identity Mapping -> Customer -> Real Delivery Phone
```

يجب أن يسمح `Customer` بامتلاك رقم هاتف حقيقي للاستلام ومعرف تحويل واحد أو أكثر، مع نوع المعرّف ومصدره عند الحاجة. عدم العثور على mapping نتيجة واضحة باسم `Unresolved`، وليس سببًا لتخمين العميل أو إرسال الخدمة إلى معرف غير قابل للإرسال.

#### القوالب الافتراضية المرجعية

تُراجع الصيغ الحالية في الكود أولًا قبل اعتماد أي قالب. الأمثلة المستهدفة التي يجب تغطيتها باختبارات عند إثبات ملاءمتها هي:

- حاسب: استخراج مبلغ مثل `200` ومعرف حساب مثل `120025`.
- الكريمي: استخراج مبلغ مثل `7400` واسم/معرف المودع.
- ون كاش: استخراج المبلغ مع دعم الصيغة العشرية وتحديد اسم المودع.
- أم فلوس: استخراج المبلغ والاسم مع وجود المرجع.
- جوالي: التمييز بين رقم هاتف مباشر واسم/حساب مخفي.
- جيب: التمييز بين رقم الهاتف والنص الواقع بعد الشرطة.

هذه الأمثلة مرجعية للسلوك وليست تصريحًا بأن القوالب موجودة حاليًا. لا يُسمح بإضافتها إلى الإنتاج قبل التحقق من الصيغ الفعلية وعينات رسائل حقيقية منزوعة البيانات الحساسة.

#### الأعمال المطلوبة عند بدء المرحلة

- مراجعة SMS Bridge ومصدر الرسائل والتحويلات الواردة.
- البحث عن كل Parser أو Regex أو Template Engine أو Customer Identifier موجود حاليًا.
- فصل تحليل الرسالة عن حل هوية العميل وعن Workflow الدفع وتسليم الكرت.
- إنشاء نموذج موحد للرسالة المحللة، أو تطوير النموذج الحالي إن كان يؤدي الغرض.
- بناء Template Engine عام للقوالب الافتراضية والمخصصة.
- دعم `%amount` و`%phone` و`%account` مع تصنيف `identifierType` صريح.
- إنشاء أو توسيع Customer Identity Mapping باستخدام Models وRepositories الحالية دون تكرارها.
- منع إرسال SMS إلى معرف غير قابل للإرسال.
- الحفاظ على idempotency وAudit وProcessing Status والاستعادة بعد الانقطاع.
- تسجيل نتيجة التحليل وسبب الفشل بطريقة قابلة للتشخيص.
- عدم تغيير مخطط قاعدة البيانات أو إضافة Migration قبل إثبات الحاجة من فحص البنية الحالية.

**معيار القبول:** تتحول الرسالة الخام إلى نتيجة منظمة ومصنفة، ثم تُحل إلى عميل ورقم تسليم عند وجود mapping، أو تتوقف بحالة `Unresolved` قابلة للتشخيص، دون تخمين أو تكرار أو إنشاء Architecture موازية.

#### قاعدة اختيار فئة الكرت وتسلسل التسليم

عند وصول تحويل مالي ناجح، يستخرج النظام قيمة المبلغ من الرسالة، ثم يبحث عن `CardCategory` موجودة فعليًا في قاعدة البيانات وتساوي قيمة التحويل. فئات الكروت لا تُنشأ تلقائيًا من التحويلات، بل يضيفها المستخدم من شاشة الكروت، وترتبط بها الكروت المستوردة.

مثال:

```text
تحويل بقيمة 200 ريال
  -> البحث عن CardCategory بقيمة 200
  -> اختيار كرت متاح من الفئة بسياسة FIFO المعتمدة
  -> حجز الكرت مؤقتًا
  -> إرسال الكرت إلى رقم العميل المحلول
  -> عند نجاح الإرسال فقط: Mark Sold + Sale + Ledger/Transaction + Audit
```

القواعد الإلزامية:

- لا يُستخدم `categoryId` ثابت أو فئة وهمية أو فئة يتم تخمينها من الكود.
- إذا لم توجد فئة مطابقة، لا يُحجز أي كرت وتُسجل حالة قابلة للتشخيص مثل `unmatched_amount` أو `pending` وفق النموذج المعتمد.
- إذا وُجدت الفئة دون كرت متاح، لا يُنفذ البيع وتُسجل حالة `out_of_stock` أو `pending` مع السبب.
- الحجز المؤقت لا يساوي البيع؛ لا تصبح حالة الكرت `sold` ولا تُسجل Sale النهائية قبل نجاح إرسال SMS.
- عند فشل الإرسال، تبقى العملية قابلة لإعادة المحاولة أو تُسجل `failed/retriable`، ولا تُحتسب كبيع ناجح، مع تحرير الحجز أو معالجته وفق سياسة الاسترداد.
- يجب استخدام `operationId` ثابت لمنع تكرار البيع أو الإرسال عند إعادة استقبال الرسالة أو إعادة المحاولة.
- يجب منع بيع الكرت نفسه في عمليتين متزامنتين، ومعالجة انتهاء الحجز.

التسلسل المفصول هو:

```text
SMS Parsing
  -> Customer Resolution
  -> Amount-to-Category Resolution
  -> Card Reservation
  -> SMS Delivery
  -> Mark Sold
  -> Sale / Ledger / Audit
```

لا يرسل Parser الكرت ولا يتخذ القرار التجاري؛ يمرر النتيجة إلى الخدمات الحالية مثل `LocalSaleService` و`CardInventoryService` و`MessageSender` و`SmsBridge` بعد فحص عقودها، دون إنشاء Architecture موازية.

حالات الفشل التي يجب اختبارها تشمل: مبلغ غير مطابق، مخزون منتهٍ، عميل غير محلول، فشل الحجز، فشل SMS، تكرار الرسالة، إعادة المحاولة بنفس `operationId`، انتهاء الحجز، نجاح الإرسال مع فشل تسجيل النتيجة، والتزامن على الكرت نفسه.

### المرحلة 6B: الأنظمة التشغيلية المستخلصة من مرجع Kurotek

هذه الأفكار تُضاف إلى خارطة NET كمتطلبات مستقبلية قابلة للتقييم، وليست دليلًا على وجودها حاليًا في المشروع. تُنفذ فقط بعد فحص Domain وDatabase وRepositories الحالية، وبنفس مبدأ Local-first وFeature-by-feature.

#### 1. التحقق من مصدر الرسالة

يجب أن يتضمن استقبال SMS طبقة تحقق من `Sender ID` أو رقم المرسل قبل تمرير الرسالة إلى التحليل، متى كانت بيانات Android والمحفظة تسمح بذلك. الهدف هو تقليل رسائل الاحتيال أو الرسائل التي تشبه رسائل المحافظ.

هذا التحقق لا يستبدل تحليل القالب، ولا يجوز اعتباره ضمانًا أمنيًا مطلقًا؛ يجب تسجيل نتيجة التحقق، واعتبار المصدر غير الموثوق حالة رفض أو تعليق وفق سياسة المنتج.

#### 2. مسارات المعالجة الآلية والتفويض المعلق

يجب دعم مسارين واضحين للتحويلات الواردة:

- **Auto-Send:** يُنفذ تلقائيًا عندما يكون القالب موثوقًا، والمبلغ مطابقًا لفئة بيع معتمدة، وهوية العميل محلولة، والمخزون متاحًا، وجميع قواعد الأمان والتكرار ناجحة.
- **Pending Approval:** تُعلّق العملية عندما يكون المبلغ غير معتمد، أو المعرّف غير محلول، أو الإرسال الآلي معطلًا، أو توجد مخاطرة تحتاج قرارًا بشريًا.

حالة التعليق لا تخصم المخزون نهائيًا ولا ترسل الكرت تلقائيًا. يجب أن تحتوي على سبب واضح، ومدة صلاحية، وسجل تدقيق، وإمكانية التأكيد أو الرفض من داخل التطبيق. يمكن دراسة إشعار تفاعلي لاحقًا، لكن لا يُفترض دعم أزرار الإشعار أو تنفيذها قبل التحقق من قيود Android.

#### نطاق هذه الإضافة

تقتصر هذه الإضافة على التحقق من مصدر الرسالة ومسار `Pending Approval` المرتبط بالتحويلات الواردة. لا تُضاف أي أنظمة أخرى من المرجع إلى خطة NET.

## 8. معايير منع الانحراف عن الهدف

- ممنوع نسخ البيانات الافتراضية من Kotlin إلى Flutter على أنها بيانات حقيقية.
- ممنوع إنشاء Mock Data في الإنتاج؛ يسمح فقط بـFixtures معزولة للاختبارات.
- ممنوع ربط العمليات المالية مباشرة بأزرار الواجهة دون Use Case ومعاملة قاعدة بيانات.
- ممنوع افتراض API أو Backend غير موثق.
- ممنوع حذف شاشة من المرجع قبل تحديد البديل وحالة التنقل الخاصة بها.
- ممنوع اعتبار نجاح عرض الشاشة نجاحًا للميزة.
- لا تُقبل أي ميزة دون اختبارات وحالات فشل واضحة.
- لا تُقبل أي معالجة SMS دون idempotency وaudit trail واستعادة بعد الانقطاع.

## 10. أول خطوة عملية بعد الموافقة

لن تبدأ الخطوة الأولى بكتابة Flutter. ستبدأ بإعداد **وثيقة قرار المنتج والدومين** التي تحتوي على:

1. قائمة الشاشات ومساراتها المستخرجة من Kotlin.

3. جدول الكيانات والحقول والعلاقات.
4. حالات دورة البيع والتحويل والحجز والعكس.
5. قرارات الإنترنت والعمل دون اتصال.
6. قائمة الأسئلة التي تحتاج عينات أو قرارًا من صاحب المنتج.

بعد اعتماد هذه الوثيقة، يبدأ تصميم قاعدة البيانات ثم محرك الأعمال، وبعد ذلك فقط تُربط واجهات Flutter.

## 11. افتراضات الخطة

- Android هو المنصة الأولى، ولا توجد في المرحلة الأولى متطلبات iOS لمعالجة SMS.
- التطبيق يحتاج تشغيلًا يوميًا دون إنترنت.
- مزود الشبكة هو المستخدم الأساسي، وقد يكون التطبيق لمستخدم واحد على الجهاز في البداية.
- مستودع Kotlin مرجع واجهة، وليس مصدرًا للبيانات أو المنطق غير المثبت.
- أي ميزة في مواصفات NET لا تظهر في Prototype ستحتاج Domain وUI جديدين، ولا تُحشر قسرًا في شاشة موجودة.
- لا يتم اختيار Backend أو مزود SMS أو مكتبة Flutter نهائية قبل إغلاق القرارات المذكورة في جدول المخاطر.

## 12. النتيجة المتوقعة

بنهاية الخطة، يكون التطبيق نظام Android حقيقيًا وليس مجموعة شاشات: بيانات محلية موثوقة، معاملات مالية ذرية، مخزون قابل للتدقيق، معالجة SMS قابلة للاستعادة، ترخيص آمن، واجهات Flutter محافظة على تجربة Kotlin، واختبارات تغطي دورات التشغيل الحرجة.

لن يبدأ التنفيذ قبل موافقة المستخدم على هذه الخطة وعلى القرارات المعمارية التي تغير نطاق المشروع أو طريقة التشغيل.
